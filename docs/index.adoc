== Introduction

The k8s-1m project is a research effort to scale Kubernetes to 1 million nodes.
This requires making several non-standard architectural decisions around networking, state management, and scheduling.

Each ADR follows this format:
- *Status*: Proposal/Accepted/Deprecated/Superseded
- *Context*: The problem or motivation
- *Decision*: The chosen solution
- *Consequences*: Trade-offs (positive, negative, neutral)
- *Related Decisions*: Links to other ADRs
- *References*: Links to code, documentation, external resources

== Executive Summary

The k8s-1m project tackles three fundamental bottlenecks that limit Kubernetes scalability:

1. **Networking**: IPv4 address exhaustion at 1M nodes → Solution: Use IPv6 exclusively
2. **State Management**: etcd write throughput limits (~50K/sec) → Solution: Custom in-memory etcd (mem_etcd)
3. **Scheduling**: Single-threaded kube-scheduler can't schedule 1M pods quickly → Solution: Distributed scheduler with scatter-gather pattern

These decisions collectively enable scaling Kubernetes to 1 million nodes while maintaining performance and reliability.

== ADR Index

=== ADR-0001: Use IPv6 Exclusively for Cluster Networking

xref:adr/0001-use-ipv6-addressing.adoc[Read ADR-0001: Use IPv6 Exclusively]

*Status*: Accepted

*Summary*: Use IPv6 exclusively for all cluster networking in the k8s-1m project.

*Key Trade-off*: Vast address space (2^64 per subnet) vs. IPv4 compatibility requirements.

=== ADR-0002: Use Custom In-Memory etcd (mem_etcd) Instead of Standard etcd

xref:adr/0002-use-mem-etcd-instead-of-standard-etcd.adoc[Read ADR-0002: Use mem_etcd]

*Status*: Accepted

*Summary*: Replace standard etcd with a custom in-memory implementation for ephemeral Kubernetes state.

*Key Trade-off*: 20x+ write throughput vs. no durability across restarts.

=== ADR-0003: Implement Distributed Scheduler Using Scatter-Gather Pattern

xref:adr/0003-implement-distributed-scheduler.adoc[Read ADR-0003: Distributed Scheduler]

*Status*: Accepted

*Summary*: Replace default kube-scheduler with a distributed scheduler using scatter-gather pattern.

*Key Trade-off*: Near-linear scaling (1M pods in 60s) vs. increased system complexity.

== Conclusion

The three ADRs documented here represent the core architectural shifts needed to scale Kubernetes to 1 million nodes:

- **IPv6 networking** eliminates address space constraints
- **mem_etcd** provides the write throughput needed for massive scale
- **Distributed scheduler** parallelizes pod placement across the cluster

Together, these decisions demonstrate that with the right architectural choices, Kubernetes can scale far beyond conventional limits. The k8s-1m project continues to explore the boundaries of what's possible.
